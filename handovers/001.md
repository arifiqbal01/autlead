1. Project Overview

Autlead is a self-hosted, modular B2B lead-generation and lead-intelligence engine.

The long-term purpose is to support two products:

WebArtsy — web development, SEO, ecommerce, ERP, software development, and digital services.
Autply — AI-powered unified inbox/customer-support automation.

Autlead is intended to collect companies/leads from multiple external sources, normalize and deduplicate them, enrich them with useful information, analyze opportunities, qualify them, and eventually generate personalized outreach.

However, the project is being developed incrementally.

The immediate goal is deliberately much smaller:

Get a reliable list of real businesses into PostgreSQL.

The first useful system is:

External Business Discovery Provider
            ↓
         Extract
            ↓
    Pydantic validation
            ↓
       Normalization
            ↓
       Deduplication
            ↓
          Company
            ↓

            ↓
       Lead export

Only after this base system works reliably should Autlead grow into:

The project intentionally avoids reinventing specialized extraction technology. Existing capable open-source repositories should be integrated as providers wherever practical.

3. Core Architecture

Autlead is a modular monolith, not a collection of microservices.

The primary organizing principle is ETL:

              AUTLEAD
                 │
        ┌────────┼────────┐
        ↓        ↓        ↓
     EXTRACT  TRANSFORM  LOAD
        │        │        │
        │        │        │
        │        ├─ Normalize
        │        ├─ Deduplicate
        │        ├─ Analyze
        │        ├─ Enrich
        │        ├─ Signals
        │        ├─ Score
        │        └─ Qualify
        │
        └────────┴──────────────→ PostgreSQL

External capabilities are integrated through providers:

Existing open-source project
            ↓
      Provider adapter
            ↓
    Autlead protocol/contract
            ↓
     Pydantic schema
            ↓
      ETL pipeline

The important architectural boundary is:

Autlead owns integration, normalization, validation, transformation, persistence, provenance, and business logic. External projects provide specialized extraction capabilities.

4. Why Modular Monolith?

A modular monolith was deliberately chosen instead of microservices.

Why

At the current scale, separate services would add infrastructure and operational complexity without providing meaningful benefits.

The system has several logically separate capabilities, but they can coexist inside one Python application.

This provides:

Simple development
Simple local execution
Shared types
Shared database
Easier debugging
Easier testing
Clear module boundaries
Future ability to extract components if genuinely required
Alternative considered

Microservices.

Why rejected

Microservices would introduce:

service deployment
service discovery
networking
duplicated configuration
distributed debugging
more operational overhead

before the product has demonstrated that such complexity is necessary.

If reversed

Moving to microservices too early would make the project harder to develop without solving the current lead-collection problem.

7. Providers Must Be Replaceable

The pipeline should depend on a capability rather than a specific provider.

Conceptually:

          ↑
     ┌────┴─────┐
     │          │
 Google Maps  Directory

The pipeline should not know whether the data came from:

The provider translates external output into Autlead's own structures.

8. Protocols

Protocols are allowed and encouraged where they protect a real capability boundary.

Example:

class BusinessDiscoveryProvider(Protocol):
    async def discover(
        self,
        query: DiscoveryQuery,
    ) -> list[BusinessRecord]:
        ...

However, Autlead deliberately does not use a giant global:

app/ports/
app/adapters/
app/interfaces/

architecture.

Why

That was considered unnecessarily abstract and fragmented for this project.

Protocols should generally live close to the capability they describe.

For example:

app/providers/discovery/
├── protocol.py
├── google_maps.py
└── ...
Important

Do not introduce protocols simply because "clean architecture" says every dependency needs an interface.

Create them when they provide an actual architectural benefit.

31. Important Architectural Decisions Log
Decision 1 — Modular monolith

Decision: Keep Autlead as a modular monolith.

Why: Current scale does not justify microservices.

Alternative: Microservices.

Why rejected: Operational complexity without current benefit.

If reversed: Development, testing, and deployment become significantly more complicated.

Decision 2 — ETL as primary architecture

Decision: Organize the system around Extract → Transform → Load.

Why: The core problem is collecting and transforming external data into useful lead records.

Alternative: Generic service-oriented architecture.

Why rejected: ETL maps directly to the business workflow.

If reversed: Responsibilities become harder to reason about and extraction/transformation/load boundaries become less clear.

Decision 3 — Use open-source providers

Decision: Integrate existing open-source projects.

Why: Specialized extraction is already solved in many cases.

Alternative: Build custom scrapers/crawlers/verifiers.

Why rejected: Reinventing complex and fragile technology wastes development effort.

If reversed: Autlead becomes a scraping technology project instead of a lead-generation system.

Decision 4 — Providers are replaceable

Decision: External projects are implementations, not core architecture.

Why: Providers may disappear, become unreliable, change APIs, or have poor coverage.

Alternative: Directly couple pipelines to one library.

Why rejected: Creates vendor/provider lock-in.

If reversed: Replacing a provider would require rewriting application logic.

Decision 5 — Protocols, but no generic ports layer

Decision: Use Python protocols where useful, but do not create a global ports/ architecture.

Why: Protocols protect real capability boundaries; a global ports/adapters structure would add unnecessary fragmentation.

Alternative: Full Clean Architecture/Hexagonal Architecture directory structure.

Why rejected: Too much architecture for the current project.

If reversed: The project becomes more abstract and fragmented than necessary.

Decision 6 — No premature abstractions

Decision: Don't create generic factories, registries, managers, DI containers, etc. without a demonstrated need.

Why: One implementation does not justify an abstraction framework.

Alternative: Build the complete abstraction layer first.

Why rejected: Speculative architecture creates maintenance cost.

Decision 7 — PostgreSQL as source of truth

Decision: PostgreSQL owns persistent application state.

Why: It is the authoritative database.

Alternative: CSV/JSON/local files.

Why rejected: Poor consistency, querying, concurrency, and persistence semantics.

Decision 8 — Pydantic at boundaries

Decision: Use Pydantic for structured data boundaries.

Why: External data is unreliable and should be validated before entering the system.

Alternative: Raw dictionaries everywhere.

Why rejected: Weak typing and difficult-to-debug transformations.

Decision 9 — Minimal configuration

Decision: Only configure services when they are active.

Why: Avoid configuration clutter and scope creep.

Alternative: Put all future settings into .env immediately.

Why rejected: Makes future infrastructure appear active and increases maintenance.

Decision 10 — Celery/Redis deferred

Decision: Do not use Celery/Redis in the initial base version.

Why: First prove the ETL pipeline.

Alternative: Start with distributed workers.

Why rejected: No current need.

Decision 11 — Intelligence deferred

Decision: Do not start with Ollama/LLM intelligence.

Why: Intelligence is useless if the underlying lead data is unreliable.

Alternative: Generate pitches immediately.

Why rejected: Produces sophisticated output from bad inputs.

Decision 12 — Deterministic scoring before ML

Decision: Use rules/heuristics initially.

Why: No outcome dataset exists yet.

Alternative: ML lead scoring.

Why rejected: No training/evaluation data.

Decision 13 — Deterministic normalization

Decision: Normalize simple data deterministically.

Why: URL/domain/name/phone normalization does not require an LLM.

Decision 14 — Simple deduplication first

Decision: Start with domain, phone, source ID, name/address.

Why: Easy to understand and test.

Alternative: AI entity resolution from day one.

Why rejected: Complexity is not justified before seeing real failure cases.

Decision 15 — Human-reviewed outreach first

Decision: Outreach eventually starts with human review.

Why: Protects sender reputation and allows evaluation of personalization quality.

Alternative: Fully autonomous sending.

Why rejected: Too risky before lead quality is proven.

35. Environment Variable Gotcha

At one point:

uv run python -c "import asyncio; from sqlalchemy.ext.asyncio import create_async_engine; import os; asyncio.run((lambda e: e.dispose())(create_async_engine(os.environ['DATABASE_URL'])))"

failed with:

KeyError: 'DATABASE_URL'

This means the environment variable was not available to that command.

The important lesson:

Having .env in the repository does not automatically mean arbitrary Python code using os.environ has loaded it.

Application configuration should use Pydantic Settings/dotenv handling rather than assuming:

os.environ["DATABASE_URL"]

will always exist.

Do not randomly duplicate .env loading throughout the project.

40. Known Landmine — Do Not Build the Future Architecture Yet

The repository already contains directories for future capabilities.

This can tempt a developer/agent to "finish" them.

Do not.

For example:

app/state/
app/transform/scoring/
app/transform/qualification/

do not mean all of those systems should currently be implemented.

The execution plan determines what is active.

41. Known Landmine — Do Not Add Redis/Celery Configuration

Do not add:

REDIS_URL
CELERY_BROKER_URL
CELERY_RESULT_BACKEND

just because Celery/Redis are installed.

They are future infrastructure.

42. Known Landmine — Do Not Add Ollama Configuration

Do not add:

OLLAMA_BASE_URL
OLLAMA_MODEL

until the intelligence phase begins.

43. Known Landmine — Do Not Create a ports/ Directory

This was explicitly considered and rejected.

Protocols are fine.

A giant ports/adapters structure is not currently wanted.

Keep protocols close to their capability.

44. Known Landmine — Do Not Turn Providers into Business Logic

A provider should not contain:

WebArtsy scoring
Autply scoring
lead qualification
outreach decisions
product messaging

It should translate external data into Autlead structures.

45. Known Landmine — Do Not Put Everything Into Pipelines

Pipelines should coordinate stages.

Do not make:

pipeline.py

a 1,000-line file containing:

scraping
normalization
database queries
scoring
provider-specific logic
business rules

Keep modules responsible for their actual concern.

46. Known Landmine — Don't Over-Model

The system has:

domain/
persistence/
schemas/

but this does not mean every tiny data structure needs three versions.

Model separation should solve an actual boundary problem.

Avoid creating:

DomainFoo
PersistenceFoo
FooSchema
FooDTO
FooResponse
FooCommand
FooResult

for every simple concept unless the boundaries genuinely require them.

47. Known Landmine — Don't Over-Abstract

If there is one concrete implementation and no meaningful replacement problem, a concrete implementation is acceptable.

Do not create:

AbstractManager
BaseProviderFactory
GenericRepositoryFactory
UniversalService

just to make the code look architecturally sophisticated.

48. Known Landmine — Don't Build a Custom Scraper First

The project specifically decided against reinventing extraction technology.

Before writing a scraper:

Search for an appropriate open-source project.
Evaluate its current capabilities.
Evaluate whether it provides the required output.
Wrap it in a provider.
Normalize its output.

Only build custom extraction when an actual gap exists.

49. Known Landmine — PostgreSQL Is the Truth

Do not start passing:

CSV → script → JSON → another script → CSV

around as the application's internal data architecture.

The intended flow is:

Provider
 ↓
Autlead data
 ↓
PostgreSQL
 ↓
Exports

Exports are outputs.

50. Known Landmine — Real Data Matters

Do not assume an extraction provider is good simply because it runs successfully.

A provider can technically work while producing:

incomplete records
bad websites
duplicate companies
incorrect phone numbers
poor categories
malformed URLs

Real provider output must be inspected.

59. Final Architectural Philosophy

Autlead should be:

Modular without being fragmented.

Abstract where abstraction protects a real boundary.

Concrete where abstraction provides no current value.

Provider-independent without building a provider-management framework prematurely.

ETL-oriented without turning every function into an ETL framework abstraction.

Data-driven rather than assumption-driven.

Evidence-driven rather than LLM-driven.

Built around PostgreSQL rather than temporary files.

Able to grow into asynchronous processing without requiring asynchronous infrastructure from day one.

Able to integrate many open-source providers without being permanently coupled to any one of them.

Most importantly:

Do not build the sophisticated Autlead that might exist six months from now. Build the smallest reliable Autlead that can produce a useful lead list today.

The first success condition is simply:

Real businesses
      ↓
Open-source provider
      ↓
Autlead extraction
      ↓
Pydantic validation
      ↓
Normalization
      ↓
Deduplication
      ↓
PostgreSQL
      ↓
Useful lead list

Everything else should grow from that working foundation.
