1. Project Overview

Autlead is a self-hosted, modular B2B lead intelligence and lead-generation platform.

It is being built as a modular monolith with a strong ETL architecture:

EXTRACT
   ↓
VALIDATE
   ↓
TRANSFORM
   ↓
LOAD
   ↓
OBSERVE
   ↓
SIGNAL
   ↓
SCORE
   ↓
QUALIFY
   ↓
INTELLIGENCE
   ↓
OUTREACH

Not every pipeline needs every stage.

The platform is intended to support multiple products/ICP strategies while sharing infrastructure:

WebArtsy — web development, SEO, ERP, software development, digital services.
Autply — AI-powered unified inbox/customer-support automation.

The core philosophy is:

External/open-source capability
        ↓
Provider adapter
        ↓
Autlead protocol
        ↓
Autlead Pydantic schema
        ↓
Pipeline
        ↓
PostgreSQL

Autlead should integrate existing capable open-source extraction technology rather than reinvent it. This applies to business discovery, crawling, technology detection, verification, search, and eventually LLM inference.

The current implementation has moved significantly beyond the original MVP-0 discovery-only stage. The current working path now includes:

       ↓

2. Core Architecture
2.1 Architectural style

Autlead is a modular monolith.

Do not turn it into microservices.

Current conceptual architecture:

                         AUTLEAD

3. Provider Architecture

Providers answer:

How do we obtain this information?

They should not answer:

What does this information mean for the business?

For example:

Technology Provider
       ↓
WordPress detected

not:

Technology Provider
       ↓
WebArtsy opportunity = 80

Product-specific interpretation belongs to signals, policies, scoring, and qualification.

4. Core Engineering Principles
4.1 Do not reinvent extraction technology

If a capable open-source project already performs the required task, integrate it.

Examples:

Google Maps extraction
Website crawling
Technology detection
Search
Email verification
LLM inference

Autlead owns:

provider integration
normalization
validation
deduplication
provenance
observations
signals
scoring
qualification
orchestration
persistence
reliability

External projects own specialized extraction/detection/crawling/inference.

4.2 Providers are replaceable

The pipeline should depend on a capability, not a specific implementation.

Example:

WebsiteTechnologyDetectionProvider
             ↓
     Wappalyzer provider
             OR
     Another detector

Do not spread Wappalyzer-specific logic throughout the application.

4.3 Protocols define capabilities

Use Python Protocol when a stable provider boundary is actually required.

Example:

class WebsiteTechnologyDetectionProvider(Protocol):
    provider_name: str


    async def detect(
        self,
        website: str,
        *,
        timeout: int = 30,
    ) -> list[DetectedTechnology]:
        ...

The protocol must contain attributes that pipeline code legitimately requires. This was specifically discovered with provider_name: if the pipeline needs it, it belongs in the protocol.

4.4 No speculative abstraction

Do not introduce:

Generic provider registries without a real requirement
Generic provider managers
Generic repository factories
Complex DI containers
Event buses
CQRS
Event sourcing
Kafka
Kubernetes
Microservices
ML scoring
Vector databases
RAG infrastructure
Generic workflow engines

unless actual requirements demonstrate the need.

A small concrete implementation is preferred.

20. Lighthouse Decision
Decision — PageSpeed replaces Lighthouse as the active performance provider

Why:

Local Lighthouse requires Chrome/Chromium.
The development Mac cannot install the required current Playwright Chromium.
Lighthouse's browser dependency creates unnecessary environment coupling.
Google PageSpeed Insights exposes Lighthouse-based performance/SEO results through an HTTP API.
The PageSpeed provider has already passed a real saved-company integration test.
What happens if reversed?

If Lighthouse is reintroduced as the primary provider, the application becomes dependent on:

Node/Lighthouse installation
Chrome/Chromium
compatible browser version
CHROME_PATH or automatic browser discovery
Docker/browser image management

That is possible later, but currently unnecessary.

A Dockerized Lighthouse provider can remain an optional future implementation.

25. Wappalyzer Parsing

The provider:

Executes Docker.
Captures stdout/stderr.
Applies timeout.
Kills the process on timeout.
Raises RuntimeError on non-zero exit.
Parses JSON.
Validates the top-level mapping.
Validates technology details.
Normalizes versions.
Normalizes confidence.
Filters invalid category/group values.
Produces DetectedTechnology[].

This parsing is intentionally defensive.

Do not assume provider JSON is trustworthy.

40. Pipeline Philosophy

Pipelines coordinate.

They should not implement providers internally.

Good:

Pipeline
   ↓
Provider
   ↓
Result
   ↓
Loader

Bad:

Pipeline
   ↓
Docker commands
   ↓
HTTP requests
   ↓
HTML parsing
   ↓
provider-specific JSON
   ↓
database logic

Pipelines should remain readable.

A developer should be able to understand:

discover
   ↓
analyze
   ↓
enrich
   ↓
verify
   ↓
score

without navigating dozens of abstractions. The project specifically warns against giant pipeline files.

41. Current Pipeline Pattern

The common pipeline pattern is:

class PipelineResult(BaseModel):
    ...

then:

async def run_x_pipeline(
    *,
    provider: SomeProvider,
    ...,
    session: AsyncSession,
) -> PipelineResult:
    ...

Use Pydantic result models at meaningful boundaries.

42. Transaction Pattern

Database-writing pipelines generally use:

async with session.begin():

This is intentional.

Unit tests must therefore mock/provide an async transaction context.

A previous test failure occurred because:

session = SimpleNamespace()

did not provide:

session.begin()

The correct test helper creates an async context manager around session.begin().

Do not remove transactions merely to make unit tests simpler.

43. Partial Failure Philosophy

For batch pipelines:

Company A → success
Company B → failure
Company C → success

should generally be possible.

A single provider failure should not necessarily terminate the entire batch.

However, error details should eventually be recorded rather than silently discarded.

Current early pipeline result objects only count failures.

Future observability should include:

company_id
stage
provider
error type
error message
attempt
duration
44. Observations vs Signals

This is a fundamental boundary.

Observation:

WordPress detected

Signal:

WordPress + poor performance
        ↓
possible_web_modernization_opportunity

Observation:

performance_score = 56

Signal:

poor_mobile_performance

Do not skip directly from providers to sales conclusions.

Observations are factual evidence.

Signals are interpretations derived from evidence.

58. Known Landmine — SQLAlchemy Transaction State

A PageSpeed integration test once failed with:

sqlalchemy.exc.InvalidRequestError:
A transaction is already begun on this Session.

Cause:

The test accessed/modified the SQLAlchemy session before calling a pipeline that itself uses:

async with session.begin():

SQLAlchemy can automatically begin a transaction after operations such as queries/flushes.

When writing integration tests:

inspect the fixture's transaction behavior
avoid beginning a nested transaction accidentally
don't blindly add session.begin() around code that already owns the transaction

The pipeline's transaction boundary should remain explicit.
