1. Project Overview

Autlead is a self-hosted, modular B2B lead-intelligence and lead-generation platform.

The project is designed to support multiple products/ICP strategies while sharing common infrastructure. The current primary product being developed is WebArtsy, which targets businesses that may need web development, e-commerce, SEO, branding, software, or related digital services.

The project is intentionally a modular monolith, not a microservices system.

The architectural philosophy is:

EXTRACT
   ↓
VALIDATE
   ↓
TRANSFORM
   ↓
LOAD
   ↓
ANALYZE
   ↓
ENRICH
   ↓
SCORE
   ↓
QUALIFY
   ↓
INTELLIGENCE
   ↓
OUTREACH

Not every pipeline needs every stage.

The current active WebArtsy flow is:

Google Maps discovery

Contacts
        ↓
Technology
        ↓
Performance / SEO

The next major development focus is better people discovery, not rebuilding the existing crawling system.

2. Core Architecture
2.1 Modular monolith

Autlead currently follows:

                    AUTLEAD
                       │
        ┌──────────────┼──────────────┐
        │              │              │
    Providers       Pipelines       Models
        │              │              │
        └──────────────┼──────────────┘
                       │

                       │

Do not turn this into microservices.

Do not introduce distributed infrastructure merely because the project may eventually scale.

The project explicitly prefers:

modularity

The original architecture documents explicitly warn against prematurely adding Kubernetes, Kafka, microservices, CQRS, event sourcing, vector databases, RAG, ML scoring, complex state machines, Celery orchestration, or Redis workflows.

5. CLI Architecture — Important Recent Decision

The CLI was deliberately refactored so that app/main.py is thin.

The intended structure is:

app/main.py
    ↓
app.cli
    ↓
command-specific module
    ↓
pipeline

Current command modules:

app/cli/
├── __init__.py
├── discovery.py
└── webartsy.py

The main CLI should primarily:

configure logging
build the top-level parser
dispatch to the selected command

It should not contain WebArtsy pipeline implementation.

The top-level command interface is:

uv run python -m app.main discovery ...

and:

uv run python -m app.main webartsy ...
6. CLI Parser Convention

Command modules expose:

def build_parser(
    parser: argparse.ArgumentParser | None = None,
) -> argparse.ArgumentParser:
    ...

This is intentional.

It allows both:

parser = build_parser()

and:

subparser = build_parser(parser=subparser)
Previous problem

The CLI originally defined:

def build_parser() -> argparse.ArgumentParser:

Then the top-level CLI tried:

build_webartsy_parser(
    parser=webartsy_parser,
)

which produced:

Unexpected argument
Decision

All reusable command parsers should accept an optional parser:

parser: argparse.ArgumentParser | None = None

Do not revert this to a zero-argument-only parser.

7. Current app/main.py Pattern

The top-level entry point should remain approximately:

from __future__ import annotations


import argparse
import asyncio


from app.cli.discovery import build_parser as build_discovery_parser
from app.cli.discovery import run as run_discovery
from app.cli.webartsy import build_parser as build_webartsy_parser
from app.cli.webartsy import run as run_webartsy
from app.core.logging import configure_logging




def build_parser() -> argparse.ArgumentParser:
    parser = argparse.ArgumentParser(
        description="Autlead command-line interface.",
    )


    subparsers = parser.add_subparsers(
        dest="command",
        required=True,
    )


    discovery_parser = subparsers.add_parser(
        "discovery",
        help="Run the business discovery pipeline.",
    )


    build_discovery_parser(
        parser=discovery_parser,
    )


    webartsy_parser = subparsers.add_parser(
        "webartsy",
        help="Run the WebArtsy lead pipeline.",
    )


    build_webartsy_parser(
        parser=webartsy_parser,
    )


    return parser




async def async_main() -> None:
    parser = build_parser()
    args = parser.parse_args()


    if args.command == "discovery":
        await run_discovery(args)
        return


    if args.command == "webartsy":
        await run_webartsy(args)
        return


    parser.error(
        f"Unknown command: {args.command}"
    )




def main() -> None:
    configure_logging()
    asyncio.run(async_main())




if __name__ == "__main__":
    main()

The exact implementation may evolve, but main.py must remain thin.

10. Company Failure Isolation

A major architectural decision:

A failure for one company must not terminate the entire WebArtsy run.

The company-level portion has a failure boundary:

Company A
    ↓
success


Company B
    ↓
403 / timeout / parsing error
    ↓
record failure
    ↓
continue


Company C
    ↓
success

Failures are represented by:

WebArtsyCompanyFailure

with:

company_id
company_name
website
stage
error_type
error_message

When a company transaction fails:

await session.rollback()

must occur before continuing.

This is intentional and must be preserved.

12. Website Retention

Website crawling uses a retention policy.

The relevant logic is:

website crawl state
        ↓
last crawl
        ↓
retention policy
        ↓
crawl again?

If the existing crawl is still fresh:

should_recrawl_website(...)

returns false.

Then the pipeline reuses:

get_website_crawl_content(...)

rather than crawling again.

This is important.

The existing website content is already a reusable analysis input.

13. IMPORTANT NEW DECISION — People Extraction Must Reuse Existing WebsiteContent

This is one of the most important decisions from 2026-08-19.

Do NOT crawl a website again for people extraction.

The current website-analysis stage already produces:

WebsiteContent

The people extractor must consume that existing content.

Correct:

Website
   ↓
Crawl4AI
   ↓
WebsiteContent
   ├── contacts extraction
   └── people extraction

Incorrect:

Website
   ↓
Crawl4AI
   ↓
WebsiteContent
   ↓
people extractor
   ↓
crawl website again

There is no reason to make people extraction perform another crawl when the pipeline already has:

HTML
text
links
URL

available.

This decision supersedes any older people-extraction test/design that described the extractor itself as fetching team pages. The crawler may fetch additional URLs when explicitly instructed by the website-analysis layer, but people extraction itself must not initiate a second crawl.

100. Learnings Log
Learning 1 — Gosom works

Gosom successfully runs in Docker and returns real Google Maps business data.

Learning 2 — Gosom returns rich raw data

Preserving:

raw_data

is useful because the external result contains substantially more information than the minimum Autlead model.

Learning 3 — Gosom produces duplicates

Provider-level deduplication is necessary.

Observed historical:

91 rows
90 unique place_ids
1 duplicate
Learning 4 — limit is not coverage

The limit controls accepted results, not market coverage.

Learning 5 — Location parsing bug was real

A hardcoded Lahore/PK assumption was exposed by Amsterdam testing and fixed.

Learning 6 — Email enrichment is expensive

Gosom supports email extraction, but it is deliberately not part of basic discovery.

Contact enrichment should remain a separate concern.

Learning 7 — Direct provider testing is valuable

Testing Gosom independently made provider debugging much easier.

Continue this pattern for future external providers.

Learning 8 — Grid must be measured

The useful metric is:

unique place_ids

not CSV rows.

Learning 9 — Website anti-bot behavior is common

Large sites may block Crawl4AI.

This is normal external-provider behavior and should remain an isolated company failure.

Learning 10 — Contact extraction works better than people extraction

Recent runs demonstrate that:

emails
phones
social URLs

can be extracted successfully while:

people

remain sparse.

Therefore the people-generation stage is the current bottleneck.

Learning 11 — Decision-maker scoring is not the bottleneck

The scorer correctly rejects weak candidates.

The missing candidates need to be solved upstream.

Learning 12 — Reusing WebsiteContent is the correct architecture

The crawler already gives the pipeline:

HTML
text
links
URL

Re-crawling the same website for people extraction wastes time and increases failure/anti-bot exposure.

Learning 13 — Main CLI should be thin

Putting the entire pipeline in app/main.py made the CLI difficult to maintain.

The command modules now own parser construction and command execution.

Learning 14 — Timestamped exports are useful

Every run producing:

webartsy_leads_YYYY-MM-DD_HH-MM-SS.csv

makes historical run comparison straightforward.

Learning 15 — Old development data can distort testing

Fresh development runs should be tested against known database state.

When necessary, clear application tables before controlled experiments.
