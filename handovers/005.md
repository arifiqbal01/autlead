1. Project Overview

Autlead is a self-hosted, modular B2B lead-generation and lead-intelligence platform.

It is being built as a modular monolith, not as microservices. Its purpose is to discover businesses, collect and analyze their websites, extract contacts/decision makers, normalize and resolve entities, identify useful signals, score leads, qualify them, and eventually support intelligent and human-reviewed outreach.

The long-term product/ICP consumers include:

WebArtsy — web development, SEO, ERP, software development, ecommerce, and digital services.
Autply — AI-powered unified inbox/customer-support automation.

The architectural philosophy is:

External/Open-source capability
        ↓
Provider adapter
        ↓
Autlead contract/schema
        ↓
Extract
        ↓
Transform
        ↓
Load
        ↓
Signals / Scoring / Qualification
        ↓
Intelligence
        ↓
Outreach

The project deliberately avoids rebuilding specialized extraction technology that already exists as capable open-source software. Autlead owns integration, normalization, validation, provenance, deduplication, transformation, business rules, scoring, qualification, orchestration, and persistence.

The project has now progressed beyond the original discovery-only MVP. Business discovery, website crawling/analysis, technology observations, and a people/decision-maker extraction pipeline are actively being developed.

The current immediate focus is improving people extraction quality before expanding that pipeline further.

2.2 Provider philosophy

Providers answer:

How do we obtain this information?

They should not answer:

What does this information mean for the business?

Example:

Technology Provider
        ↓
WordPress detected

is provider/extraction work.

WordPress detected
        ↓
Potential WebArtsy opportunity

belongs to signals/policies/scoring.

Providers are replaceable implementations.

Examples:

BusinessDiscoveryProvider
        ↓
Gosom

or eventually:

BusinessDiscoveryProvider
        ↓
Another provider

The pipeline must not become coupled to Gosom, Crawl4AI, a particular search engine, or another external implementation.

4. Core Architecture Decisions
Decision 1 — Modular monolith

Decision: Keep Autlead as a modular monolith.

Why: Current scale does not justify microservices.

Alternative considered: Microservices.

Rejected because: They add deployment, networking, observability, testing, and development complexity without solving a current problem.

If reversed: Local development and debugging become substantially harder, and simple pipelines become distributed systems unnecessarily.

Decision 2 — ETL is the primary organizing model

Decision: Organize the application around Extract → Transform → Load.

Why: Autlead's fundamental problem is obtaining external data and progressively transforming it into reliable lead intelligence.

Alternative: Generic service-oriented architecture.

Rejected because: ETL gives clearer ownership boundaries.

If reversed: Provider extraction, transformation, enrichment, and persistence responsibilities become harder to reason about.

Decision 3 — Integrate existing extraction technology

Decision: Prefer capable open-source projects over custom extraction implementations.

Why: Crawling, browser automation, Maps extraction, verification, search, etc. are specialized and fragile.

Alternative: Build everything internally.

Rejected because: It wastes development effort and changes Autlead into a scraping framework.

If reversed: Autlead inherits unnecessary maintenance of specialized extraction infrastructure.

This is an explicit core engineering principle.

Decision 4 — Providers are replaceable

Decision: External projects are implementations, not architectural foundations.

Why: Providers can change, disappear, have coverage problems, or produce poor results.

Alternative: Couple pipelines directly to individual providers.

Rejected because: Provider replacement would then require rewriting application logic.

If reversed: Pipeline logic becomes provider-specific.

Decision 5 — Capability protocols instead of generic architecture layers

Use Python Protocol when a real capability boundary exists:

class BusinessDiscoveryProvider(Protocol):
    async def discover(
        self,
        query: DiscoveryQuery,
    ) -> list[BusinessRecord]:
        ...

Do not introduce generic:

app/ports/
app/adapters/
app/interfaces/

just for architectural aesthetics.

Do not create:

ProviderFactory
ProviderManager
ProviderRegistry
UniversalRepository
GenericService

until a concrete requirement justifies one.

Decision 6 — Gosom is the current Google Maps provider

Decision: Gosom Google Maps Scraper is the active business-discovery implementation.

Previous alternative: gmaps_extractor.

Status: Previous implementation is superseded.

Gosom is accessed through its provider adapter and Docker runtime.

The application should depend on:

BusinessDiscoveryProvider

rather than Gosom directly.

Decision 7 — Docker is currently provider infrastructure, not a mandate to Dockerize Autlead

Gosom runs through Docker because that is a practical way to use the external project.

Do not interpret this as a requirement to containerize the entire Autlead application.

Decision 8 — PostgreSQL is the source of truth

CSV and other provider outputs are intermediate/external data, not the application's long-term data architecture.

Preferred:

Provider
   ↓
Autlead schema
   ↓
PostgreSQL
   ↓
Export

Do not create:

CSV → script → JSON → script → CSV

as the internal architecture.

Decision 9 — Provider-level deduplication and application deduplication are different

Inside Gosom/provider:

Provider results
    ↓
provider-specific deduplication

Inside Autlead:

BusinessRecord
    ↓
existing Company?
    ↓
existing SourceRecord?
    ↓
insert/update

These must not be collapsed into one mechanism.

Decision 10 — Deterministic normalization before intelligent reasoning

Normalization such as:

domain
URL
phone
company name
person name
person title

should be deterministic.

Do not use an LLM for simple normalization.

Decision 11 — Simple deterministic deduplication first

Company identity should initially use signals such as:

domain
phone
name
address
source identifier

More sophisticated entity resolution should be introduced only when real data demonstrates the need.

Decision 12 — Deterministic scoring before ML

There is currently no sufficiently mature outcome dataset to justify ML lead scoring.

Current approach:

rules / heuristics

not:

machine learning

The people scoring implementation is deterministic.

Decision 13 — Evidence-based conclusions

Do not store conclusions without evidence.

Prefer:

signal
evidence
source
confidence
timestamp
rule/version

rather than an unexplained:

Good lead = true
Decision 14 — Celery/Redis are deferred architecturally

Celery and Redis may exist in the environment/dependencies, but they are not required to define the current application architecture.

Do not introduce worker complexity merely because the packages are installed.

Future preferred structure:

Pipeline
   ↓
Celery task
   ↓
Application operation
   ↓
Provider

The task should remain thin.

Decision 15 — Intelligence/LLM is deferred

LLMs may eventually produce:

lead summaries
pain hypotheses
offer angles
personalization
message drafts

But they should not be used to rediscover deterministic facts.

Long-term division:

Facts          → deterministic
Observations   → deterministic
Signals        → rules
Scoring        → deterministic
Reasoning      → LLM
Writing        → LLM
Decision 16 — Outreach starts human-reviewed

Future outreach should initially be:

Generated draft
      ↓
Human review
      ↓
Approval
      ↓
Send
      ↓
Track

Do not immediately make outbound communication fully autonomous.

8. Circular Import Landmine

A circular dependency occurred during the refactor.

The bad dependency was effectively:

names.py
    ↓
titles.py
    ↓
names.py

Specifically, names.py imported:

from .titles import extract_nearby_title, find_titles

while titles.py imported functions from names.py, including:

clean_name_candidate

This produced:

ImportError:
cannot import name 'clean_name_candidate'
from partially initialized module
Required rule

names.py and titles.py must not mutually import each other.

A clean direction should be:

patterns.py
words.py
    ↓
titles.py
names.py
linkedin.py
    ↓
website.py

If a shared primitive is needed by both, move the primitive to an independent module rather than creating a cycle.

Do not "solve" this by randomly adding local imports unless there is a deliberate reason.

10. Current Title Regex Bug

A major real-world false positive was observed:

GDPR Cookie Consent

was extracted as:

name = GDPR Cookie Consent
title = COO

This is almost certainly caused by COO being matched inside cookie.

Therefore title regexes must use true word boundaries / lookarounds around abbreviation titles.

Preferred structure:

(?<![\wÀ-ÖØ-öø-ÿ])
...
(?![\wÀ-ÖØ-öø-ÿ])

rather than relying only on a loose \b.

This is especially important for:

CEO
CTO
CMO
COO
CFO
VP
Dr

Do not fix this by removing legitimate titles.

12. Recommended Immediate Name Fix

names.py should be aware of normalized title vocabulary without creating a circular import.

A helper such as:

def _title_tokens() -> set[str]:
    tokens: set[str] = set()


    for language in ("en", "nl"):
        for title in title_mapping(language).keys():
            tokens.update(
                title.casefold().split()
            )


    return tokens

can identify title tokens.

Then trailing role words can be removed from an extracted candidate:

Jana Stickelbruck Vestigingsmanager
            ↓
Jana Stickelbruck
Maarten Vaartjes Tandarts
            ↓
Maarten Vaartjes

Do this carefully: the extraction function should trim an obvious trailing role rather than simply reject the entire candidate.

The recent recommendation was to add something conceptually equivalent to:

def _trim_trailing_title_words(
    words: list[str],
) -> list[str]:
    title_words = _title_tokens()


    while len(words) > 2:
        if _comparison_word(words[-1]) not in title_words:
            break


        words.pop()


    return words

Then apply it before final validation in clean_name_candidate().

This work is recommended but not yet verified by a subsequent test run.

15. LinkedIn Handling

People extraction recognizes LinkedIn /in/ profile URLs.

Current normalization accepts:

https://linkedin.com/in/john-smith/
https://www.linkedin.com/in/john-smith/?trk=...

and canonicalizes to:

https://www.linkedin.com/in/john-smith

Query parameters and fragments are discarded.

Only /in/ profiles are accepted.

LinkedIn is preferred as an identity key when available.

16. Person Identity

Current deterministic identity concept:

LinkedIn exists
    ↓

otherwise:

identity = ("name", normalized_name)

This is not entity resolution.

It is an extraction/identity key.

Do not make person_identity() perform fuzzy matching.
