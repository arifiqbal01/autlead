1. Project Overview

Autlead is a self-hosted, modular B2B lead intelligence and lead-generation engine.

It is intended to support multiple internal products/ICP strategies while sharing common infrastructure:

WebArtsy — web development, SEO, ERP, software development, and digital services.
Autply — AI-powered unified inbox/customer-support automation.

The project is intentionally being built as a modular monolith, not as microservices.

The central architectural model is:

EXTRACT
   ↓
VALIDATE
   ↓
NORMALIZE
   ↓
DEDUPLICATE
   ↓
ANALYZE
   ↓
ENRICH
   ↓
VERIFY
   ↓
SCORE
   ↓
QUALIFY
   ↓
INTELLIGENCE
   ↓
OUTREACH

Not every pipeline needs every stage.

The current active work is much earlier:

Google Maps
    ↓
Gosom provider
    ↓
BusinessRecord
    ↓
Discovery pipeline
    ↓
Company + SourceRecord
    ↓
PostgreSQL

The current priority is to make business discovery reliable and scalable enough for real internal lead generation before building website analysis, contacts, scoring, LLM intelligence, or outreach.

The project deliberately integrates capable open-source extraction technology instead of rebuilding scrapers from scratch. This is a core architectural principle.

10. Current Gosom Execution

The provider creates a temporary directory:

autlead-gosom-XXXX/
├── queries.txt
└── results.csv

It writes:

dentists in Amsterdam, Netherlands

to queries.txt.

Then it executes approximately:

docker run --rm \
  -v "$queries_file:/queries.txt:ro" \
  -v "$results_directory:/out" \
  gosom/google-maps-scraper \
  -input /queries.txt \
  -results /out/results.csv \
  -depth 1 \
  -c 1 \
  -exit-on-inactivity 3m

The provider waits for Docker to finish asynchronously.

It has a configurable timeout:

600 seconds

It converts:

timeout;
OS/process failure;
non-zero Gosom exit;
missing results file;
CSV read errors

into BusinessDiscoveryProviderError.

This keeps Gosom-specific operational behavior inside the provider.

11. Current Gosom Data Mapping

Gosom CSV data is mapped approximately as follows:

Gosom                  Autlead
----------------------------------------

website           →    website
website hostname  →    domain
phone             →    phone
address           →    address
category          →    category
place_id          →    external_id

The provider extracts the domain using urllib.parse.urlparse.

Example:

https://www.example.com/
        ↓

The provider also parses the requested location.

For:

it produces:

city = Amsterdam
country = Netherlands

For:

Lahore, Pakistan

it produces:

city = Lahore
country = Pakistan

This replaced an earlier hardcoded implementation that incorrectly stored Amsterdam businesses as:

city = Lahore
country = PK

That issue is now fixed.

12. Important Location Decision

The provider currently derives city and country from:

query.location

rather than trying to infer them from every business address.

This is intentionally simple at the current stage.

Example:

python app/main.py "dentists" "Amsterdam, Netherlands"

means the discovery query's geographic context is:

Amsterdam
Netherlands

and those become the normalized BusinessRecord location fields.

This should not be "improved" into complex geocoding unless real requirements demonstrate the need.

The business's full physical address is still preserved separately.

18. Email Extraction — Current State

Gosom supports an email extraction option.

Its documented behavior is:

-email

and email extraction is disabled by default.

The scraper documentation says enabling it makes the scraper visit each business website to find email addresses, and that it significantly increases processing time.

Autlead currently does NOT enable -email.

This is intentional for the current discovery test.

The raw source record observed during the Autlead test contained:

"emails": ""

So:

Google Maps discovery
        ↓
website
        ↓
phone
        ↓
business data

is currently active, while:

website
   ↓
email extraction

is not yet active.

Do not silently add -email merely because the field exists.

Email/contact discovery is a later pipeline stage.

19. Gosom Result Limits

A critical distinction:

--limit 50

in Autlead means:

Return/store at most 50 businesses from the provider's returned results.

It does not mean:

Gosom's result count depends on:

Google Maps search behavior;

depth;

Therefore:

Autlead limit

and:

are two different concerns.

This is why geographic/grid testing is now the next important task.

22. Current Grid Architecture Decision

Grid support is implemented in the provider, but its usefulness has not yet been fully validated.

Do not assume:

grid = automatically better

The correct question is:

Does grid produce significantly more unique businesses
than a normal search for the same geographic area?

Only real data should answer that.

If grid significantly improves coverage, then expose it through the Autlead CLI.

If it provides little improvement, do not add unnecessary grid complexity.

Provider-level deduplication

Inside Gosom provider:

   ↓

   ↓

   ↓

29. Architecture Decisions Log
Decision 1 — Modular monolith

Decision: Keep Autlead as a modular monolith.

Why: Current scale does not justify microservices.

Alternative: Microservices.

Rejected because: Operational complexity would be added without solving the current lead collection problem.

If reversed: Development, testing, deployment, debugging, and local development all become more complicated.

Decision 2 — ETL is the primary organizing model

Decision: Organize the system around ETL.

Why: The fundamental problem is collecting external business data and progressively transforming it into useful leads.

Alternative: Generic service-oriented architecture.

Rejected because: ETL maps more directly to the business workflow.

If reversed: Extraction, transformation, enrichment, and persistence responsibilities become less explicit.

Decision 3 — Use existing open-source extraction technology

Decision: Integrate existing open-source projects instead of rebuilding them.

Why: Scraping, crawling, verification, and similar capabilities are complex and fragile.

Alternative: Build custom Google Maps scraping/browser automation.

Rejected because: It wastes effort and turns Autlead into a scraping framework.

If reversed: Autlead would inherit unnecessary browser/extraction maintenance.

This principle is explicitly documented as a core project rule.

Decision 4 — Gosom replaced the previous Maps extractor

Decision: Use Gosom Google Maps Scraper as the current discovery implementation.

Why: It successfully produced rich Google Maps data through a practical Docker interface and passed real Lahore and Amsterdam tests.

Previous alternative: gmaps_extractor.

Superseded: The previous GoogleMapsExtractorDiscoveryProvider is no longer the active implementation.

If reversed: The current working Gosom integration would be lost and the provider would return to the previous extractor's interface/behavior.

Decision 5 — Docker is currently only an external provider runtime

Decision: Run Gosom through Docker locally.

Why: Gosom is already available as a Docker image and Autlead itself is a Python application. This avoids bringing Go build/runtime concerns into Autlead.

Alternative: Install/build Gosom directly as a Go binary/package.

Rejected for now: No practical benefit for the internal local project.

Alternative: Dockerize all of Autlead.

Rejected for now: There is no current deployment requirement requiring it.

If reversed: The provider integration and local development setup become unnecessarily coupled to a larger containerized infrastructure.

Decision 6 — Providers are replaceable

Decision: External projects are implementations, not core architecture.

Why: Providers can fail, change, disappear, or have poor geographic/data coverage.

Alternative: Directly couple pipelines to Gosom.

Rejected: Creates provider lock-in.

If reversed: Replacing Gosom would require rewriting pipeline logic.

Decision 7 — Use a capability protocol

Decision: BusinessDiscoveryProvider defines the discovery contract.

Why: The pipeline needs business discovery, not specifically Gosom.

Alternative: Call Gosom directly from the pipeline.

Rejected: Would leak provider-specific details into application logic.

Decision 8 — No generic ports/ or giant adapter architecture

Decision: Keep protocols close to their capabilities.

Example:

app/providers/discovery/
    protocol.py
    gosom.py

Why: The project does not currently need a large Clean Architecture/Hexagonal directory hierarchy.

Alternative: Global:

app/ports/
app/adapters/
app/interfaces/

Rejected: Too abstract and fragmented.

Decision 9 — No provider registry/factory/manager yet

Do not create:

ProviderRegistry
ProviderFactory
ProviderManager
ProviderRouter
ProviderMarketplace

until actual provider-selection requirements exist.

One implementation does not justify an abstraction framework.

Decision 10 — PostgreSQL is source of truth

Decision: PostgreSQL owns persistent application state.

Alternative: CSV/JSON files.

Rejected: Files are poor as an application database.

CSV is useful for exports and provider interchange, not as the application's authoritative store.

Decision 11 — Pydantic at boundaries

Decision: External provider output becomes BusinessRecord.

Why: External data is unreliable and should be validated.

Alternative: Raw dictionaries everywhere.

Rejected: Weak typing and harder debugging.

Decision 12 — Minimal configuration

Only configure active infrastructure.

Do not add future settings simply because the architecture may eventually need them.

Do not currently add:

REDIS_URL
CELERY_BROKER_URL
CELERY_RESULT_BACKEND
OLLAMA_BASE_URL
OLLAMA_MODEL

until those capabilities become active.

Decision 13 — Celery/Redis deferred

Decision: Do not use Celery/Redis yet.

Why: First prove the ETL pipeline.

Alternative: Start with distributed workers.

Rejected: No demonstrated workload requires them.

If reversed: Adds deployment and operational complexity before the business workflow is validated.

Decision 14 — Intelligence deferred

Do not introduce Ollama/LLM intelligence yet.

Why: Bad lead data produces sophisticated bad output.

The sequence is:

reliable data
    ↓
reliable analysis
    ↓
reliable signals
    ↓
intelligence
Decision 15 — Deterministic normalization

Normalize:

company names;
URLs;
domains;
phones;
locations.

Use deterministic code rather than an LLM.

Decision 16 — Deterministic deduplication first

Start with:

source identifier
domain
phone
name/address

Do not build AI/entity-resolution infrastructure before real data demonstrates a need.

Decision 17 — Human-reviewed outreach

When outreach eventually becomes active:

Generated draft
     ↓
Human review
     ↓
Approval
     ↓
Send
     ↓
Track

Fully autonomous outreach is explicitly not the initial design.

Decision 18 — Real-world validation is mandatory

A provider is not considered successful merely because the process exits with code 0.

Real data must be inspected for:

missing websites;
bad websites;
incorrect phone numbers;
duplicate businesses;
bad categories;
malformed URLs;
incorrect geographic metadata.

This is why the Lahore and Amsterdam tests were performed.

31. Learnings Log
Learning 1 — Gosom works in Docker

Direct Docker execution successfully found businesses in Lahore.

This validated Gosom as a practical discovery backend.

Learning 2 — Gosom produces rich raw data

The CSV includes significantly more than the minimal Autlead fields.

This makes preserving raw_data useful.

Learning 3 — Gosom can return duplicates

Observed:

CSV rows: 91
Unique place_ids: 90
Duplicates: 1

Therefore provider-level deduplication is necessary.

Learning 4 — Autlead limit is not Gosom coverage

--limit 10 controls how many returned records Autlead processes.

It does not guarantee that Gosom discovered only 10 or exactly 10.

Coverage needs to be evaluated separately.

Learning 5 — Location must not be hardcoded

The first Amsterdam test exposed a bug where:

Amsterdam business

was stored as:

Lahore / PK

The fix was to parse:

query.location

into:

city
country

The latest Amsterdam output confirms this works.

Learning 6 — Email extraction is expensive and currently disabled

Gosom supports:

-email

but it is intentionally not enabled.

Email extraction should eventually be considered part of contact enrichment rather than basic discovery.

Learning 7 — Direct provider testing is valuable

Testing Gosom independently before integrating it into Autlead made it easier to establish:

Gosom works

before debugging:

Autlead + Docker + provider + database

This testing pattern should continue for other providers.

Learning 8 — Grid coverage must be measured, not assumed

A grid can produce many duplicate results.

The relevant metric is:

unique place_ids

not simply:

CSV rows

The Amsterdam grid experiment is still pending.

Learning 9 — SQLAlchemy logging is currently verbose

The pipeline works despite extensive SQL logging.

This is a logging configuration issue, not evidence of database failure.

32. Known Issues / Landmines
Landmine 1 — Do not hardcode country/city

Never put:

country="PK"
city="Lahore"

into the generic Gosom provider.

The current implementation correctly derives these from the query location.

Landmine 2 — Do not pass old provider arguments

Do not do:

GosomGoogleMapsDiscoveryProvider(
    proxy=args.proxy,
    workers=args.workers,
    enrich=not args.no_enrich,
    verbose=True,
)

unless those arguments are actually supported by the current Gosom constructor.

The previous gmaps_extractor provider had a different interface.

Landmine 3 — Do not assume --limit increases Gosom coverage

This:

--limit 500

does not force Gosom to discover 500 businesses.

Coverage needs:

query variation;
geographic grid;
depth;
possibly multiple searches;
deduplication.
Landmine 4 — Do not enable email extraction casually

Adding:

-email

will significantly increase processing time because Gosom visits websites.

Only enable it when contact discovery is intentionally being implemented.

Landmine 5 — Do not Dockerize Autlead just because Gosom uses Docker

Current architecture:

Python Autlead
    ↓
Docker subprocess
    ↓
Gosom

This does not imply:

Dockerize all Autlead

Keep the distinction clear.

Landmine 6 — Do not build grid before measuring it

Grid support already exists in the provider.

Do not immediately make it the default.

First compare:

normal search
vs
grid search

using:

unique place_ids
Landmine 7 — Do not treat raw CSV as application storage

CSV is an extraction/output artifact.

The pipeline should persist normalized records into PostgreSQL.

Landmine 8 — Do not add Celery/Redis yet

They are installed but deferred.

Do not add environment variables or application configuration merely because the packages exist.

Landmine 9 — Do not add Ollama yet

Intelligence is downstream of trustworthy data.

Landmine 10 — Do not create custom Maps scraping

Gosom is already solving that problem.

Only replace it if real data demonstrates a meaningful gap.

Landmine 11 — Do not build a generic provider system

There is currently one active discovery provider.

A capability protocol is enough.

Landmine 12 — Do not assume provider success means data quality

Always inspect actual output.

41. One-Paragraph Resume Summary

Autlead is a Python 3.12/uv modular-monolith B2B lead intelligence system using PostgreSQL, SQLAlchemy async, Pydantic, and provider-based ETL. The current active vertical slice is Google Maps business discovery using GosomGoogleMapsDiscoveryProvider, which runs gosom/google-maps-scraper through a local Docker subprocess, converts its CSV output into BusinessRecord, deduplicates by provider identifiers such as place_id, and persists companies/source records to PostgreSQL. The basic Lahore and Amsterdam tests work, including correct dynamic city/country parsing; a previous hardcoded Lahore/PK bug is fixed. A direct Gosom test showed 16 Lahore places, and another test showed 91 CSV rows / 90 unique place_ids / 1 duplicate. Gosom email extraction is available but deliberately disabled. The immediate unfinished task is to compare normal Amsterdam search against a small geographic grid and measure unique place_id coverage. If grid materially improves coverage, expose --grid-bbox, --grid-cell-km, and --zoom through the CLI. Do not Dockerize the whole Autlead application yet; Docker is currently only the runtime wrapper for Gosom. Do not add Celery/Redis, Ollama, scoring, contact discovery, website analysis, or outreach until the discovery pipeline and real-world coverage are validated. PostgreSQL remains the source of truth, providers remain replaceable, Pydantic remains the boundary schema, and new abstractions must be justified by real requirements.
