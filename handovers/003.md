# 1. Project Overview

**Autlead** is a self-hosted, modular B2B lead intelligence and lead-generation engine.

It is intended to support multiple products/ICP strategies while sharing common infrastructure:

* **WebArtsy** — web development, SEO, ERP, software development, and digital services.
* **Autply** — AI-powered unified inbox/customer-support automation.

Autlead is intentionally a **modular monolith with asynchronous execution planned/available**, not a microservices system.

The core architectural model is:

```text
EXTRACT
   ↓
VALIDATE
   ↓
TRANSFORM
   ↓
LOAD
   ↓
PostgreSQL
```

As the lead engine grows, the pipeline becomes:

```text
DISCOVER
   ↓
NORMALIZE
   ↓
DEDUPLICATE
   ↓
ANALYZE
   ↓
OBSERVE
   ↓
SIGNAL
   ↓
ENRICH
   ↓
VERIFY
   ↓
SCORE
   ↓
QUALIFY
   ↓
INTELLIGENCE
   ↓
OUTREACH
```

Not every product pipeline needs every stage.

The central architectural principle is that Autlead should **integrate capable open-source extraction technology instead of rebuilding it**. Autlead owns provider adapters, schemas, normalization, evidence, signals, policies, orchestration, persistence, and reliability—not specialized scraping technology.

# 4. Core Architectural Principles

## 4.1 Modular monolith

Autlead remains a modular monolith.

Do not split it into microservices.

**Why:** Current complexity does not justify distributed application architecture.

**Alternative considered:** Microservices.

**Rejected because:** It would add deployment, networking, debugging, testing, and operational complexity without solving the current problem.

**If reversed:** Almost every subsystem becomes harder to develop and operate.

---

## 4.2 ETL is the organizing principle

The system is organized around:

```text
Extract
   ↓
Transform
   ↓
Load
```

Additional analysis/policy/state layers surround this flow.

**Why:** Autlead's fundamental problem is turning external information into structured lead intelligence.

**Alternative:** Generic service-oriented architecture.

**Rejected:** ETL provides clearer boundaries between extraction, transformation, and persistence.

---

## 4.3 Do not reinvent extraction technology

If a capable open-source project already performs the task, integrate it.

Examples:

* Google Maps extraction
* Website crawling
* Technology detection
* Search
* Contact discovery
* Email verification
* LLM inference

Do not build custom versions without a demonstrated gap. This is an explicit project rule. 

---

## 4.4 Providers are replaceable

Providers are implementations of capabilities, not architectural foundations.

Example:

```text
WebsiteCrawlerProvider
        ↓
Crawl4AI
```

could later become:

```text
WebsiteCrawlerProvider
        ↓
Another crawler
```

without changing the pipeline contract.

---

## 4.5 Protocols define capabilities

Use `Protocol` only where an abstraction is actually useful.

Example:

```python
class WebsiteCrawlerProvider(Protocol):
    async def crawl(
        self,
        request: CrawlRequest,
    ) -> WebsiteContent:
        ...
```

Do not create an enormous generic interface hierarchy.

---

## 4.6 No generic `ports/` architecture

Do **not** create:

```text
app/ports/
app/adapters/
app/interfaces/
```

merely for architectural purity.

Protocols should normally live close to their capability.

---

## 4.7 Avoid speculative abstractions

Do not prematurely create:

* Provider factories
* Generic provider registries
* Generic managers
* Universal repositories
* Generic workflow engines
* Event buses
* CQRS
* Event sourcing
* Microservices
* Kafka
* Kubernetes
* Temporal
* ML orchestration
* Universal policy engines

An actual second implementation or concrete requirement should justify abstraction.

# 9. Separate `website_crawl_links` Table

The links were deliberately separated from `website_crawls`.

Conceptually:

```text
website_crawls
    ↓
website_crawl_links
```

A crawl contains the page-level content.

The link table contains individual discovered links.

This avoids putting a potentially large list of links into one database column and allows links to be queried independently.

Do not move the links back into the `WebsiteCrawl` table simply for convenience.

# 10. Why Crawl HTML Is Persisted

A major design decision was made during the crawl work:

> Save the crawl result rather than crawling the website from the beginning every time.

The persisted crawl contains:

```text
HTML
Text
Title
Meta description
Status
Content hash
Provider
Collected timestamp
Links
```

This allows later stages to reuse the crawl.

For example:

```text
Crawl once
   ↓
save HTML/text
   ↓
technology detection
   ↓
SEO analysis
   ↓
signal extraction
   ↓
LLM/intelligence later
```

without repeatedly fetching the website.

This is especially important because crawling is relatively expensive.

# 16. Website Crawl Valid Transitions

Current valid transition map:

```python
VALID_TRANSITIONS: dict[
    WebsiteCrawlStatus,
    set[WebsiteCrawlStatus],
] = {
    WebsiteCrawlStatus.PENDING: {
        WebsiteCrawlStatus.RUNNING,
    },
    WebsiteCrawlStatus.RUNNING: {
        WebsiteCrawlStatus.COMPLETED,
        WebsiteCrawlStatus.FAILED,
        WebsiteCrawlStatus.RETRYING,
    },
    WebsiteCrawlStatus.FAILED: {
        WebsiteCrawlStatus.RETRYING,
    },
    WebsiteCrawlStatus.RETRYING: {
        WebsiteCrawlStatus.RUNNING,
        WebsiteCrawlStatus.FAILED,
    },
    WebsiteCrawlStatus.COMPLETED: set(),
}
```

And:

```python
def can_transition(
    current: WebsiteCrawlStatus,
    new: WebsiteCrawlStatus,
) -> bool:
    return new in VALID_TRANSITIONS[current]
```

The `COMPLETED` state is terminal.

This is tested.

# 17. Important State Transition Semantics

Current lifecycle:

```text
PENDING
   ↓
RUNNING
   ↓
COMPLETED
```

Failure:

```text
RUNNING
   ↓
FAILED
```

Retry:

```text
RUNNING
   ↓
RETRYING
   ↓
RUNNING
```

Retry exhaustion:

```text
RETRYING
   ↓
FAILED
```

Invalid examples:

```text
COMPLETED → RUNNING
COMPLETED → FAILED
COMPLETED → RETRYING
PENDING → COMPLETED
PENDING → FAILED
RUNNING → PENDING
FAILED → RUNNING
```

These are explicitly tested.

# 20. Important State Improvement Still Needed

The current state functions assign the status directly:

```python
state.status = WebsiteCrawlStatus.RUNNING.value
```

etc.

The transition system exists and is thoroughly tested, but the mutation functions should eventually **use the transition validator**, rather than independently assigning arbitrary status strings.

Desired direction:

```text
state operation
     ↓
read current status
     ↓
can_transition(...)
     ↓
perform transition
```

This prevents a future state operation from accidentally bypassing the state machine.

Do this before expanding the state system further.

# 23. Retention vs State

These must remain separate.

Retention answers:

```text
Should we fetch the website again?
```

State answers:

```text
What is the current execution state of the crawl?
```

Persistence answers:

```text
What crawl result do we already have?
```

Provider answers:

```text
How do we fetch it?
```

Orchestration combines them.

# 26. `_get_last_crawl`

The orchestration code initially referenced:

```python
_get_last_crawl
```

without defining it.

That helper needs to exist.

The simplest current implementation is:

```python
async def _get_last_crawl(
    session: AsyncSession,
    state: WebsiteCrawlState,
) -> WebsiteCrawl | None:
    if state.last_crawl_id is None:
        return None

    return await session.get(
        WebsiteCrawl,
        state.last_crawl_id,
    )
```

This is reasonable because `WebsiteCrawlState.last_crawl_id` already identifies the latest successful crawl.

# 41. Discovery Deduplication

There are two distinct deduplication layers.

## Provider-level

Gosom output is deduplicated using its stable place identity.

Conceptually:

```text
Gosom results
    ↓
place_id deduplication
    ↓
BusinessRecord[]
```

## Application/database-level

Autlead then performs its own deduplication:

```text
BusinessRecord
    ↓
existing Company?
    ↓
existing SourceRecord?
    ↓
```

# 45. Load Transactions

Database operations should use explicit transaction boundaries.

```text

   ↓

   ↓
```

Failure:

```text

```

# 46. Important Crawl Transaction Consideration

The crawl provider is external and may take several seconds.

Do not hold a database transaction open unnecessarily while the external crawler runs.

Preferred conceptual sequence:

```text
set state RUNNING
commit
   ↓
external crawl
   ↓
load crawl
   ↓
mark state COMPLETED
commit
```

On failure:

```text
crawl exception
   ↓
mark state FAILED/RETRYING
commit
```

This avoids keeping a database transaction open during network/browser execution.



This separation is intentional.

# 67. Known Landmine — Do Not Re-Crawl Every Time

The entire purpose of the new crawl persistence/state/retention work is to prevent:

```text
Pipeline starts
   ↓
crawl website
   ↓
pipeline starts again
   ↓
crawl same website
   ↓
repeat
```

Instead:

```text
Pipeline starts
   ↓
check existing crawl
   ↓
retention policy
   ↓
reuse if fresh
```

Only crawl again when policy says the previous result is stale or unusable.

---

# 68. Known Landmine — Do Not Use HTML Cache as the Whole State System

Persisting HTML does not tell you:

```text
Was a crawl currently running?
Did the last attempt fail?
How many attempts occurred?
When should we retry?
What was the last successful crawl?
```

That is why:

```text
WebsiteCrawl
```

and:

```text
WebsiteCrawlState
```

remain separate.

---

# 69. Known Landmine — Do Not Treat `status_code == 200` as the Only Success

Real testing showed redirects such as:

```text
301
```

can still return useful content.

The crawler's result should be interpreted according to the actual provider/policy contract.

Do not hard-code:

```python
if status_code != 200:
    failure
```

without an explicit requirement.

Whether such a result should trigger retry/failure belongs to the policy/state/orchestration layer.

| No generic ports layer                     | Avoid architectural fragmentation               | More abstractions with little value                    |
| PostgreSQL source of truth                 | Durable application state                       | State becomes fragmented                               |
| Separate crawl result/state                | Data ≠ execution state                          | Cannot cleanly manage freshness/retries                |
| Separate crawl links                       | Links are repeatable child data                 | Crawl row becomes unnecessarily large                  |
| Persist HTML/text                          | Reuse expensive crawl output                    | Every downstream stage would recrawl                   |
| Content hash                               | Detect identical crawl content                  | Harder to compare crawl results                        |
| Retention policy                           | Avoid unnecessary recrawls                      | Expensive repeated crawling                            |
| Crawl state enum separate from transitions | Clear lifecycle definition                      | Status/transition logic becomes tangled                |
| Completed terminal                         | Prevent accidental reprocessing                 | Completed crawls could be incorrectly restarted        |
| Targeted State before Celery               | Crawl already needs durable lifecycle/freshness | Unnecessary recrawling/failure ambiguity               |
| State transition tests                     | Protect lifecycle semantics                     | Direct status assignments could silently corrupt state |
| Real Crawl4AI tests                        | Mocks cannot prove real websites work           | False confidence                                       |
| Separate provider/policy                   | Provider obtains facts, policy decides action   | Business logic leaks into providers                    |
| Separate pipeline/load                     | Orchestration shouldn't own persistence         | Giant pipeline modules                                 |
| No custom event loop fixture               | asyncpg loop mismatch                           | `Future attached to different loop`                    |
| Alembic required for new models            | SQLAlchemy model alone doesn't create DB table  | `UndefinedTableError`                                  |
| No Dockerize-all decision                  | Docker only needed for Gosom currently          | Deployment complexity grows prematurely                |

# 103. Learnings Log

## Learning 1 — Real crawler integration matters

Crawl4AI successfully crawled all 10 real test businesses.

Therefore the provider contract is currently viable.

---

## Learning 2 — Crawling is expensive enough to justify persistence

A 10-business integration test took about:

```text
150 seconds
```

This reinforces the decision to save crawl results and avoid unnecessary repeat crawls.

---

## Learning 3 — Crawl result and crawl state are different

A persisted crawl does not answer execution questions.

State is necessary for:

* running
* retrying
* failure
* attempt count
* last successful crawl

---

## Learning 4 — Retention is different from hashing

A content hash determines similarity.

Retention determines freshness.

Neither replaces the other.

---

## Learning 5 — Async database pools are loop-sensitive

Custom event loops caused asyncpg/SQLAlchemy failures.

Use pytest-asyncio's managed loop behavior unless there is a specific reason to override it.

---

## Learning 6 — Migrations are part of model implementation

Adding:

```text
WebsiteCrawlState
```

without creating/applying its migration resulted in:

```text
UndefinedTableError
```

Model work is incomplete until the database schema is updated.

---

## Learning 7 — State tests can pass while production state mutations bypass them

The pure transition map was fully tested, but the mutation functions directly assigned strings.

Therefore:

> Transition-map tests alone do not prove that application state mutations enforce the state machine.

This is an immediate improvement target.

---

## Learning 8 — Persistence should tolerate incomplete provider output

Real/provider-style data can contain:

```text
500
None HTML
None text
empty links
```

Persistence should preserve the result rather than inventing data.

---

## Learning 9 — Redirects can still be useful crawl results

A `301` response can have useful HTML/text/title.

Do not define crawl success solely as HTTP 200.

---

## Learning 10 — Read helpers expose architectural boundaries

The unresolved:

```text
_get_last_crawl
_website_content_from_crawl
```

showed that orchestration needs clean read APIs from Load.

This should lead toward a small PostgreSQL read operation rather than more database logic inside pipeline orchestration.

# 105. Schema Boundary Rule

Use Pydantic when data crosses meaningful capability boundaries.

Examples:

```text
CrawlRequest
WebsiteContent
BusinessRecord
DiscoveryQuery
```

Do not pass provider-specific dictionaries through the entire pipeline.

Provider output should become an Autlead schema as early as practical.

# 106. Database Boundary Rule

SQLAlchemy models represent persistence.

Pydantic schemas represent application/capability data.

Do not blindly serialize SQLAlchemy models into API/provider schemas.

Translate explicitly where the boundary matters.

# 107. Transformation Rule

Transformation answers:

```text
What should this data mean/look like inside Autlead?
```

Load answers:

```text
How do we persist it?
```

Provider answers:

```text
How do we obtain it?
```

```text
Should we perform the operation?
```

State answers:

```text
What execution state are we in?
```

Pipeline answers:

```text
What happens next?
```

Do not collapse these responsibilities.
